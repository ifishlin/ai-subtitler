# 交接

寫給下一個 session。**先讀 `CLAUDE.md`，那份是原則；這一份是現況。**

## 一、先知道這三件事

**這個專案的核心信念是：發現的錯要變成門。** 不是修這一次的症狀，是讓它
下次過不去。`CLAUDE.md` 開頭那張表就是歷史，`docs/MISTAKES.md` 是完整版
（包含擋不住的那幾項，那份比擋得住的重要）。

**視覺的錯不會報錯。** 照片被推出畫面、字被切掉、卡片全黑、成片沒有聲音 ——
沒有例外、沒有 stack trace、測試不會失敗，程式跑得完完全全成功。它們只在
有人看的時候才存在。所以**做完要真的把畫面叫出來看**，不要只看回傳值。

**做了 N 次收到 0 筆的步驟要出聲。**「找到 0 筆」和「沒有去找」在畫面上
一模一樣，而後者才是錯。

### 這個 session 改掉的文案規則（重要，下一份文案會用到）

**角色從「起承轉合」換成「吸引／建立／打破／解釋／回報」**，只影響
`assets/formats/argue.json`（新聞報導片型）；`story.json`（說故事片型，
場景／事件／疑點／懸念）完全沒動，兩者本來就各自存自己的 `structure.roles`。

```
吸引   讓人停下來：咦，這什麼？
建立   讓觀眾逐漸相信一個版本
打破   丟出跟前面預期衝突的事實 —— 必須在前 34% 出現
解釋   說清楚為什麼前後看似矛盾
回報   把新的理解收成一句值得記住的話 —— 一定是最後一句
```

`core/script.py` 的 `structure()` 完全沒改一行程式碼——它本來就是照
`rules.json`／片型檔案裡的 `roles` 清單通用寫的，`roles[2]` 自動變成
「打破」，順序檢查、`least_per_role` 都直接接上新名字。**這是故意的
設計，不是巧合**：想再加一種角色體系（第三種片型），照抄 `story.json`
的做法就行，不用碰 `core/script.py`。

**事實引用改成編號**（`from: "F3"` 這種），不再讓模型自己重打一次來源
文字。`core/brief.py` 的 `as_text()` 把事實清單印成 `[F1]`、`[F2]`……，
`core/writer.py` 的 `fasten()` 比照 `pic`／`clip`／`stock` 的做法，把
`F3` 解回真正的引用文字，編號對不上或格式不對（不是 `F\d+` 也不是
「觀點」）當場 `ValueError`，指名第幾句。這樣**寫錯出處會被抓到**——
以前 `from` 是自由文字，寫一個真的存在、但這則事實沒提過的媒體，程式
看不出來，門只檢查「有沒有寫」不檢查「寫的對不對」。

**拿掉「觀點句約一半」**，換成「核心觀點：一個」。這條從來沒被任何門
檢查過（純粹是 prompt 裡的散文），所以拿掉是零風險的純文字修改。

**JSON 輸出範例從 9 處收成 1 處**：`script.md` 的「輸出格式」那節現在
是唯一的完整 schema（`cover`／`bg`／`seen`／`outro` 都在同一個範例
裡），`visual.md` 原本 8 處各自的局部範例全部拔掉 code block，改成
文字指回 `script.md` 的 schema。

**`assets/rules.json` 的 `structure` 那段整個拿掉了**——那是片型系統
出現「之前」的舊定義，`argue.json`/`story.json` 各自都有自己的一份，
查過兩條可能用到它的路（`of()` 走 `house()` 一定 fallback 到
`argue`；`fill()` 沒傳片型的唯一呼叫點 `critic.py` 的 `review.md`
根本沒有 `{structure.*}` 佔位符）都證實用不到，才刪的。

新增一份文件：`docs/PIPELINE.md`，講 `ask`→`read`→`fasten`→`measure`→
`GATES` 這條線各自在做什麼，`/docs` 頁可以看。

## 五、這個 session 踩過的坑

**代寫文案時，把「四次獨立生成」做成了「一份骨架延伸四種長度」，被
使用者當場抓到。** 使用者因為不想用 cuba001 的模型，請我自己扮演寫手
角色，手寫 60／70／80／90 秒四份文案來驗證新規則。手寫一份能通過全部
門檻（長度、比例、色調連續張數、轉折前 34%……）很花工夫，於是我先寫
好 60 秒的骨架，驗證過關之後，70／80／90 秒都是「在同一份骨架後面加
素材」——開頭、建立、打破幾乎逐字照抄，只有 `解釋` 段變長。

結果是：四份文案的結尾（`回報` 那句「帶得走的話」）完全一模一樣，因為
根本不是四次獨立的寫作，是一份文章的四種剪法。**使用者兩次抓到**：
第一次是摘要點（`points`）一樣，我以為換掉摘要點就補完了；第二次是
連最大、最顯眼的標題／台詞（`title`／`say`）都還是一樣——那才是畫面上
真正看得到的東西。

**根因不是忘記改結尾，是方法論本身錯了**：真正的 `write()` 每次呼叫都
是獨立的、冷啟動的，模型寫 90 秒版的時候不會記得它剛剛寫過 60 秒版，
四次獨立呼叫的起手式、強調的角度都可能不一樣。我把這件事在腦子裡當成
「同一份稿子剪不同長度」（人類剪接的工作模式），而不是「模擬四次獨立
的模型呼叫」——前者省工夫，但不是使用者要測的東西。而且我沒有先把這個
取捨講出來問，就自己選了省力的做法。

**下次代寫多個長度的文案時**：當成真正獨立的四次寫作，各自從素材出發
重新決定角色怎麼安排、哪個事實當開頭、核心觀點怎麼表達——如果為了省
工夫想延伸同一份骨架，先問，不要自己決定。

**卡片配的 `clip` 跟逐字稿內容對不上**：90 秒那份文案裡，「換名字本來
該由地方發起」配了一段實際內容是「如果你記得他第一任的時候……」的
片段，兩者無關——這是我自己編造情節時，只看事實清單、沒有回頭核對
`brief.sheet()` 印出來的那段真實逐字稿內容，才配錯的。查證方式：把
`show` 文字和 passages 清單裡那段真正的 `said` 內容並排讀一遍，對不上
就換一段或改用卡片，不要硬配。

**四份測試文案本身留在 `scripts/` 底下，`git status` 顯示未追蹤**——
使用者已經指出方法論的問題，這四份**不代表驗證過的好範例**，下一個
session 不要把它們當成參考範本，也不要假設它們會被繼續使用；要不要重寫
或丟棄，等使用者決定。

## 六、跟這位使用者工作

**代寫 LLM 的角色時，把每一次生成當成獨立的、無記憶的呼叫**，不要為了
效率延伸前一次寫好的內容去湊另一個目標（另一個長度、另一種變體）。
省工夫的做法要先問，不能自己決定然後直接做。這是這個 session 最大的
教訓，見第五節。

**他常說「快問快答」。** 那表示接下來每一則都要一到兩行，除非他說「結束
快問快答」。做完事情的回報可以長一點，但也不要鋪陳。

**「先記下來，不要做」「等我說再做」是字面意思。** 討論不是授權；他把
**跑 grep、開檔案來看** 也算在「動」裡面。要查證才能回答的時候，說
「等你說我去查」，然後停住。他交代多件事的時候，先把清單覆述一次再問
要不要開始。

**回報一律附比例。** 絕對數字看不出失衡。

**跑 `checkjs.sh`／`checkview.sh`／`checkclick.sh` 這類慢速、要開瀏覽器
的檢查之前，先問。**

**被工具擋下來的時候不要繞路。** 被擋 = 停下來問，不要換一種方式達到
同樣的效果（例如 `rm -rf` 被拒之後改用 `shutil.rmtree`）。

**刪除一律走 `core/bin.py` 的 `toss()`**，移到 `trash/`，不用 `rm`。

**改檔案用 Edit 工具，不要自己寫 `t.replace(...)` 腳本**——這個坑在
更早的 session 踩過四次，每次都是 `t` 沒有被更新、後面的 replace 蓋掉
前面的結果。

**他不用 `gh` CLI，也不打算用。** 推送走 SSH。要開新 repo 的話請他自己
到 GitHub 網頁上開。

**不要一直建議他買 Claude API。**

**他有時會突然切成問我「為什麼」（為什麼做這個決定、為什麼這樣想）——
這種時候他要的是誠實的自我檢視，不是替自己的做法辯護。**
