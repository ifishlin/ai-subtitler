# 從模型的回答到一份可用的文案

`core/writer.py`、`core/script.py` 這幾支函式，順序不能換，因為
每一步的 input 就是上一步的 output：

```
prompt（script.md ＋ visual.md 填好之後的文字，core/brief.py 產生）
   │
   ▼  ask(prompt)
模型回的一大段文字 —— 前後可能夾著解釋、外面圍著 ```json ... ```
   │
   ▼  read(說的話)
一份 dict：{"view", "tone", "cover", "lines": [...]}
   │        lines 裡的 pic／clip／stock／from 都還是編號
   │        （"P18"、"C3"、"V7"、"F3"），還不是真材料
   ▼  fasten(topic, draft)
同一份 dict，編號全部換成真材料
   │        查不到就在這裡炸掉，錯誤指名第幾句 —— 不會留著一個
   │        看起來合理、其實錯誤的檔名／引用一路到成品
   ▼  measure(script)
一份「量出來的報告」：秒數、比例、每一道門過不過
   │
   ▼  GATES 逐項讀
faults = {門名: 沒過的部分}　——　空的就是全過
```

## 四支函式，各自的工作

```
ask       送 prompt，把模型回的文字原封不動拿回來。不解析、不檢查。
read      從那段文字裡挖出 JSON。模型常常會在前後加解釋、
          用 ``` 圍起來 —— 這支負責把 JSON 本體挖出來，其餘的丟掉。
fasten    把 JSON 裡的編號換成真材料：
            P18 → 檔案路徑
            C3  → 真正的起訖秒數（現查 assets/passages/，不是存死的）
            V7  → 情境影片的檔案
            F3  → 事實清單裡那一則的引用文字
          查不到、格式不對，當場丟 ValueError，指名第幾句。
measure   把 fasten 過的文案**自己身上**能算出來的每一件事都算一遍：
          總秒數、每句幾秒、借來的畫面佔幾%、影片段落佔借來畫面幾%、
          轉出現在第幾秒、字幕會不會被切掉、卡片欄位對不對……
          結果是一份大 dict，每一項門檻的答案都在裡面。
```

**`fasten` 負責「查得到、查不到」，`measure` 負責「數字夠不夠」。**
兩個都不判斷文案寫得好不好——那是人看的事。

## 門是什麼

門（`core/script.py` 的 `GATES`）不自己算東西，它只是拿 `measure()`
已經算好的答案，去對照 `assets/rules.json` 的門檻，過不過而已。

門檢查的是「**對不對得起格式**」，不是「**寫得好不好**」：

```
門檢查得到     每句有沒有標角色、有沒有標出處、比例有沒有超標、
              卡片欄位齊不齊、字幕會不會被切掉
門檢查不到     這個「轉」夠不夠有力、這個判斷是不是真的犀利、
              這個結論是不是市井小民聽得懂
```

前者數得出來、比得出來，過了就是過了；後者程式沒有算法，只能人看一遍。
`/gates` 頁列的就是這份 `GATES` 清單，每一項標了 `blocks`——
`unsourced`（陳述事實沒標來源）不擋 `build()`，其餘都擋。

## 為什麼分成兩步而不是一步查完

`fasten` 和 `measure` 是分開的兩支函式，不是因為好看：

- `fasten` 失敗是**格式錯誤**——編號打錯字、指到不存在的東西，
  這種錯誤沒有讀者會想看到成品，愈早死愈好，所以用 `raise` 直接中斷。
- `measure` 的門大多不擋（只有標了 `blocks: True` 的才擋 `build()`），
  因為那些是**判斷題**——句數不夠、比例超標，這些值得留著讓人自己看
  一遍再決定要不要重寫，而不是連原始回答都拿不到。

`write()`（`core/writer.py`）把兩步串起來：先 `fasten`（會炸的先炸），
再 `measure`（不會炸，只回報 faults），兩份都存下來——存的是
`fasten` 過的文案，`answered.raw` 存的是模型原始回答，兩份都留著，
因為 `fasten` 會失敗，而失敗的時候最想看的正是模型到底寫了什麼。
